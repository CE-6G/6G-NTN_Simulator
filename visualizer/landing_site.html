The Challenge

Space is Dynamic. Your Network Can't Be Static.

Terrestrial networks assume fixed infrastructure. In LEO constellations, satellites move at ~7.5 km/s, line-of-sight windows open and close continuously, and propagation delays fluctuate. Static routing is insufficient. Our simulator uses Dijkstra's algorithm to recompute routes dynamically, but only when the current link validity expires or SNR conditions trigger a handover — typically every 20-60 seconds. This balances routing optimality with computational cost

Continuous Topology Changes

Satellites are constantly moving. A route that is optimal now might be invalid in 30 seconds due to Earth occlusion or distance constraints.

RF Link Degradation

At 28 GHz, links are highly susceptible to atmospheric attenuation, rain fade, and Doppler shifts. SNR margins erode rapidly, requiring immediate traffic rerouting.

Complex Queueing & QoS

Maintaining latency-sensitive 6G traffic across varying hop counts and varying link capacities requires intelligent, priority-based packet scheduling.

Our Solution

We built a simulator that bridges the gap between high-fidelity orbital physics and advanced network routing. By converting real TLE data into time-varying graphs, we enable event-triggered routing and seamless handovers before links drop.

System Architecture

A Decoupled, Three-Layer Engineering Masterpiece

We didn't build a monolith. We separated physics, logic, and visualization into independent domains. This ensures that if MATLAB crashes, the Python fallback takes over. If the network drops, the 3D UI still renders. Resilience by design.

Layer 1: Physical & Orbital (MATLAB)

We leverage MATLAB's Satellite Communications Toolbox to handle the heavy astrodynamics. We don't approximate orbits; we use standard SGP4 propagators from raw TLEs.

Inputs: TLE Files (Iridium, OneWeb, Starlink)
Outputs: ECEF Positions, LOS Matrices, RF Metrics

Why MATLAB?

MATLAB provides native scenario objects, ground station primitives, and coordinate-frame aware calculations out of the box. Writing this from scratch in Python would require validating thousands of lines of custom astrodynamics code.

  • Earth Occlusion: Angular tests with a 50km atmospheric margin.
  • Link Budget: ITU-R P.618/P.676 models for rain, oxygen, and scintillation.
  • Capacity: Shannon-based limits with modulation ceilings (D2D: 10MHz, ISL_OPT: 2GHz).

Layer 2: Network & Routing (Python)

The brain of the operation. A Flask server orchestrates the simulation, converting MATLAB's flat arrays into dynamic NetworkX graphs. It handles routing, handovers, and packet-level event simulation.

API: /api/init & /api/update
Logic: Event-triggered Type-1 (Positions) & Type-2 (Links) polling

The Handover Problem

We don't wait for links to die. Our orchestrator monitors SNR windows. In "Margin" mode, if the short-window SNR drops 1dB faster than the long-window, a handover is triggered with a 3dB hysteresis to prevent flapping.

  • Routing Metrics: Min-Hop, Total Delay (ms), Distance (km) via Dijkstra.
  • Traffic: CBR and ON/OFF VBR sources with strict-priority and WRR queueing.
  • Resilience: Fallback topology generator if MATLAB Engine is unavailable.

Layer 3: Operator Visualization (CesiumJS)

We replaced static 2D plots with a fully interactive WGS84 3D globe. Operators can see the constellation move, watch links form and break, and track active routes in real-time.

Tech: CesiumJS 1.117 + Chart.js
Deployment: Static HTML (No build step required)

Why CesiumJS?

Hand-rolling Earth rendering in Three.js creates massive math overhead. Cesium natively understands ECEF coordinates, camera controls, and imagery layers, allowing us to focus purely on NTN functionality.

  • Real-time Feedback: Satellites rendered as billboards, links as polylines.
  • Analytics: Live Chart.js dashboards for throughput, latency, and packet loss.
  • Isolation: REST boundary ensures UI crashes never affect the simulation core.
